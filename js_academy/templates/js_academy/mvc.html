Architektura · przewodnik praktyczny

MVC bez
frameworka.

Model, widok i kontroler to nie trzy pliki. To trzy odpowiedzialności. Ten przewodnik pokazuje, kiedy warto je rozdzielić, jak trzymać currentView, currentSort i currentQuery w jednym stanie oraz dlaczego filtrowanie i sortowanie powinny być czystymi funkcjami.

Moduł MVC: 4 lekcje → Pełny komponent MVC ◧

Zdanie, które warto zapamiętać

Widok nie filtruje. Model nie wie o DOM. Kontroler nie liczy danych ręcznie.

Jeśli każda funkcja dostaje query, sort, page i direction osobno, sygnatury puchną, a stan i tak żyje w pięciu miejscach.

Dlaczego Kiedy Role Stan widoku Selektory Kontroler Wzorce Błędy

01 · Dlaczego

MVC kupuje przewidywalność, nie „czystość”.

W prostym widgecie możesz filtrować dane w evencie i wstawiać HTML od razu. Problem zaczyna się, gdy dochodzi drugi filtr, sortowanie, paginacja, widok grid/list i empty state. Wtedy każdy event próbuje naprawić kawałek UI, a stan jest rozrzucony po zmiennych i atrybutach DOM.

MVC porządkuje to w jeden przepływ: zdarzenie → nowy stan → selektory → render. Dzięki temu możesz odpowiedzieć na pytania: skąd pochodzi ta wartość, kto ją zmienił i dlaczego lista wygląda właśnie tak.

Testowalność

Filtrowanie i sortowanie możesz sprawdzić bez przeglądarki.

Przewidywalność

Jedno miejsce zmienia stan, jedno miejsce renderuje.

Ewolucja

Nowy filtr to pole w stanie i warunek w selektorze, nie zmiana pięciu sygnatur.

02 · Kiedy

Kiedy MVC ma sens, a kiedy jest nadmiarem.

Warto rozdzielić

  • lista ma search, kategorię, sort, grid/list i paginację,
  • ten sam stan zasila kilka fragmentów UI,
  • chcesz testować logikę bez DOM,
  • kilka osób pracuje nad jednym ekranem,
  • stan ma trafiać do URL i wracać po odświeżeniu.

Nie komplikuj

  • jeden przycisk „pokaż/ukryj”,
  • statyczna lista bez filtrów,
  • prototyp, który ma sprawdzić jeden pomysł,
  • komponent, który nie ma współdzielonego stanu.

MVC to narzędzie do zarządzania złożonością. Jeśli złożoności nie ma, nie dodawaj warstw tylko po to, by „wyglądało profesjonalnie”.

03 · Role

Trzy odpowiedzialności, nie trzy magiczne pliki.

Model

Dane i reguły

Produkty, koszyk, walidacja, uprawnienia. Model nie wie, czy lista jest grid czy list i nie dotyka DOM.

const products = [
  { id: 1, name: "Mysz", price: 89 },
  { id: 2, name: "Lampa", price: 129 },
];
View

Prezentacja

Zamienia dane na HTML. Nie filtruje, nie sortuje i nie decyduje, co się stanie po kliknięciu.

function render(state) {
  list.className = `products ${state.currentView}`;
  list.innerHTML = state.items.map(card).join("");
}
Controller

Zdarzenia i stan

Odbiera input, tworzy nowy stan, wywołuje selektory i render. Nie implementuje reguł biznesowych.

input.addEventListener("input", (event) => {
  update({ currentQuery: event.target.value });
});

04 · Stan widoku

currentView, currentSort, currentQuery — w jednym obiekcie.

To jest view state: opis tego, jak pokazać dane. Nie mieszaj go z modelem domeny. Jeden obiekt zmniejsza liczbę parametrów i wymusza spójność.

const viewState = {
  currentView: "grid",              // "grid" | "list"
  currentSort: { key: "name", direction: "asc" },
  currentQuery: "",
  currentCategory: "all",
  currentPage: 1,
  pageSize: 6,
};
currentView

Tylko prezentacja: grid/list. Nie wpływa na filtrowanie ani sortowanie.

currentSort

Obiekt { key, direction }. Sam string nie mówi, czy sortujesz rosnąco.

currentQuery

Tekst wyszukiwania. Zmiana powinna resetować currentPage do 1.

currentPage

Pochodna liczby wyników. Po filtrze może wyjść poza zakres — kontroler musi ją poprawić.

Zła sygnatura vs jeden stan

Parameter explosion 
selectProducts(
  products,
  query,
  category,
  sortKey,
  direction,
  page,
  pageSize,
  view
);

Każdy nowy filtr zmienia sygnaturę w kilku miejscach. Łatwo pominąć argument.

Jeden kontrakt 
selectProducts(products, viewState);
render(visible, viewState);

Nowe pole w stanie nie wymaga zmiany sygnatury. Funkcja selektora czyta tylko to, czego potrzebuje.

Aktualizacja przez nowy obiekt

let viewState = { ... };

function updateViewState(patch) {
  viewState = { ...viewState, ...patch };

  if (
    "currentQuery" in patch ||
    "currentCategory" in patch ||
    "currentSort" in patch
  ) {
    viewState.currentPage = 1;
  }

  render(viewState);
}

Dlaczego nowy obiekt? Łatwiej śledzić zmianę i uniknąć sytuacji, w której stara referencja została gdzieś zapamiętana. Nie mutuj stanu „przy okazji”.

05 · Selektory

Filtrowanie i sortowanie to funkcje, nie event handlery.

Selektor dostaje dane i potrzebny fragment stanu, zwraca nową listę. Nie dotyka DOM, nie czyta globali i nie zapisuje stanu.

function filterProducts(products, viewState) {
  const query = viewState.currentQuery.trim().toLowerCase();

  return products.filter((product) => {
    const matchesQuery = product.name
      .toLowerCase()
      .includes(query);

    const matchesCategory =
      viewState.currentCategory === "all" ||
      product.category === viewState.currentCategory;

    return matchesQuery && matchesCategory;
  });
}

function sortProducts(items, currentSort) {
  const factor = currentSort.direction === "desc" ? -1 : 1;

  return [...items].sort((a, b) => {
    if (currentSort.key === "price") {
      return (a.price - b.price) * factor;
    }

    return String(a[currentSort.key])
      .localeCompare(String(b[currentSort.key]), "pl") * factor;
  });
}

function paginate(items, page, pageSize) {
  const start = (page - 1) * pageSize;
  return items.slice(start, start + pageSize);
}

function selectProducts(products, viewState) {
  return paginate(
    sortProducts(filterProducts(products, viewState), viewState.currentSort),
    viewState.currentPage,
    viewState.pageSize
  );
}

Dlaczego kopia przed sortem? sort mutuje tablicę. Bez [...items] zmieniasz kolejność danych modelu i możesz zepsuć inny widok.

Dlaczego filtr nie zna currentView? Bo grid/list to prezentacja. Filtrowanie nie powinno zależeć od tego, jak wyświetlasz wynik.

Dlaczego jeden selektor? Kontroler nie skleja trzech funkcji w każdym evencie. Ma jeden kontrakt: dane + stan → widoczne dane.

06 · Kontroler i widok

Jedno miejsce zmienia stan. Jedno miejsce renderuje.

function render(viewState) {
  const visible = selectProducts(products, viewState);

  list.className = `products ${viewState.currentView}`;
  list.innerHTML = visible.map(productCard).join("");

  count.textContent = `${visible.length} produktów`;
  stateView.textContent = JSON.stringify(viewState, null, 2);
}

function updateViewState(patch) {
  viewState = { ...viewState, ...patch };
  render(viewState);
}

search.addEventListener("input", (event) => {
  updateViewState({
    currentQuery: event.target.value,
    currentPage: 1,
  });
});

sortSelect.addEventListener("change", (event) => {
  const [key, direction] = event.target.value.split(":");
  updateViewState({
    currentSort: { key, direction },
    currentPage: 1,
  });
});

viewToggle.addEventListener("click", () => {
  updateViewState({
    currentView: viewState.currentView === "grid" ? "list" : "grid",
  });
});
zdarzenie→updateViewState→selektory→render

Zwróć uwagę: zmiana currentView nie resetuje strony i nie zmienia filtra. Zmiana currentQuery resetuje stronę, bo zmienia się zbiór wyników.

07 · Wzorce

Sześć sytuacji, które wracają w każdej liście.

1. Search z debounce

Nie filtruj przy każdym znaku, jeśli dane są drogie. Opóźnij aktualizację stanu, ale nadal miej jedno źródło prawdy.

const onInput = debounce((value) => {
  updateViewState({ currentQuery: value, currentPage: 1 });
}, 250);

2. Sort toggle

Kliknięcie tej samej kolumny zmienia kierunek. Nowy klucz zaczyna od asc.

const direction =
  nextKey === currentSort.key && direction === "asc"
    ? "desc" : "asc";

3. Grid / list

currentView zmienia tylko klasę kontenera i szablon karty. Nie zmienia danych.

list.className = `products ${viewState.currentView}`;

4. Reset strony

Query, kategoria i sort zmieniają zbiór wyników. Nowy zbiór = strona 1.

if ("currentQuery" in patch) {
  viewState.currentPage = 1;
}

5. Pusty wynik

Pusty wynik to nie błąd. Pokaż go osobno i daj akcję „wyczyść filtry”.

if (!visible.length) return emptyState();

6. URL jako stan

Parametry q, sort, dir, view, page pozwalają udostępnić widok i wrócić do niego po odświeżeniu.

history.replaceState(null, "", `?${params}`);

08 · Błędy

Najczęstsze pęknięcia MVC.

  • Mutacja stanu. Zmieniasz viewState.query i oczekujesz, że „samo się odświeży”.
  • Duplikacja stanu. currentPage jest i w JS, i w atrybucie DOM. Po chwili są różne.
  • Filtrowanie w widoku. Render sam decyduje, co pokazać — nie da się tego przetestować bez DOM.
  • Sortowanie w miejscu. Brak kopii zmienia kolejność danych modelu.
  • Brak resetu strony. Po filtrze użytkownik widzi pustą stronę 7.
  • Wyścig async. Starsza odpowiedź nadpisuje nowszy query. Użyj AbortController lub identyfikatora żądania.

Test kontrolera: po zmianie query, kategorii i sortu stan musi być spójny, a currentPage musi wrócić do 1. To zachowanie można sprawdzić bez DOM, jeśli wydzielisz reducer.

09 · Testy

Co warto przetestować.

test("filtr po query", () => {
  const result = filterProducts(products, {
    currentQuery: "mysz",
    currentCategory: "all",
  });
  assert.equal(result.length, 1);
  assert.equal(result[0].name, "Mysz");
});

test("sort malejąco po cenie", () => {
  const result = sortProducts(products, {
    key: "price",
    direction: "desc",
  });
  assert.ok(result[0].price > result[1].price);
});

test("query resetuje stronę", () => {
  const next = reducer(viewState, { type: "query", value: "lampa" });
  assert.equal(next.currentPage, 1);
});

Selektory i reducer nie potrzebują przeglądarki. To najtańsze testy w całej aplikacji.
